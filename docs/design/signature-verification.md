# ตรวจสอบลายมือชื่อบนเอกสาร (หน้า `/verify` สาธารณะ)

ออกแบบร่วมกับผู้พัฒนาเมื่อ 2026-10-16 — ต่อยอดจาก `docs/design/certificates.md` และ `docs/design/document-signing.md`

## เป้าหมาย

ผู้รับเอกสาร PDF ที่ลงนามด้วยใบรับรองของ มมส. ส่วนใหญ่เป็นคนนอก เปิดใน Acrobat แล้วเห็น "ไม่ทราบความถูกต้อง" เพราะ root ของ TUC ไม่อยู่ใน AATL
หน้า `/verify` ให้ **ใครก็ได้ (ไม่ต้อง login)** อัปโหลด PDF แล้วระบบตรวจลายมือชื่อทุกรายการในไฟล์ และแสดงผลแบบเดียวกับแผงลายมือชื่อของ Acrobat

หน้าแลนดิ้ง (`/` เมื่อยังไม่ login — `components/landing/Landing.tsx`) วางกล่องตรวจไว้บนสุด แล้วอธิบายความต่างของภาพลายเซ็นกับลายมือชื่อดิจิทัล สายความเชื่อถือ (Root TUC → มมส. → ผู้ลงนาม → เอกสาร) สิ่งที่ระบบตรวจ และผล 3 ระดับ (`ResultLegend` ใช้ร่วมกับ `/verify`) — ไม่มี session หรือ cookie หมดอายุ/ถูกเพิกถอน = เห็นหน้าแลนดิ้ง (ไม่ redirect ไป `/login`), login แล้ว `/` เป็นหน้าหลักของระบบตามเดิม ส่วนหน้าอื่นที่ต้อง login ยัง redirect ไป `/login`

## การตัดสินใจ

| เรื่อง | ข้อสรุป |
|---|---|
| ที่ตรวจ | API ในหน่วยความจำ (`POST /verify/pdf`) — **ไม่เก็บไฟล์** ที่ disk/Garage/DB และไม่ log เนื้อหา (log เฉพาะขนาดและผลรวม) |
| ไม่ตรวจใน signer | signer ถือ CA key — ห้ามให้แตะไฟล์จากคนนอก |
| ไลบรารี | `pkijs` + `asn1js` (pure JS ใช้ WebCrypto ของ Node) — แยก/ตรวจ CMS, สร้างสายใบ, ตรวจ timestamp token; ไม่ใช้ OpenSSL CLI ใน API เพื่อไม่ให้โค้ด C แยกข้อมูลจากคนนอก |
| แยกลายมือชื่อจาก PDF | ไม่ตีความโครง PDF ทั้งไฟล์: หา `/ByteRange [a b c d]` แล้วอ่าน `/Contents` จากช่องว่างระหว่างช่วง (ต้องเป็น `<hex>` พอดี) และ `/ByteRange` ต้องอยู่ในส่วนที่ถูกลงนาม |
| ขีดจำกัด | ไฟล์ ≤ 20 MB (`MAX_PDF_BYTES` + nginx `client_max_body_size`), ≤ 20 ลายมือชื่อ, 30 ครั้ง / 15 นาที / IP |
| Permission | ไม่มี — **public** (CSRF: ต้องส่งจากหน้าเว็บของระบบ มี header `Origin` ตรงกับ `WEB_URL`) |
| ข้อมูลจากฐานข้อมูล | ใบที่ออกโดย Intermediate ของ มมส. ค้นสถานะจากตาราง `certificates` ด้วย serial — แสดงเฉพาะสถานะ/วัน/เหตุผลการเพิกถอน **ไม่แสดงข้อมูลบัญชีผู้ใช้** (ชื่อ/อีเมลแสดงจากใบในเอกสาร) |

## Trust anchors

| ใช้กับ | ชุด | ที่มา |
|---|---|---|
| ใบของผู้ลงนาม | root ของ TUC (+ Intermediate ของ มมส. ช่วยต่อสายใบ) | `apps/api/src/services/signature-verification/university-ca.ts` — ต้องตรงกับ `apps/signer/ca` (test ใน `apps/signer/tests/ca.test.ts`) |
| หน่วยประทับเวลา (TSA) | TUC + root สาธารณะที่มากับ Node (`tls.rootCertificates`, ชุดของ Mozilla) และ TSA ต้องมี EKU `timeStamping` | เพื่อให้ TSA สาธารณะ เช่น `timestamp.digicert.com` (ที่หน้า `/root-ca` แนะนำ) ใช้ได้ |

CA สาธารณะสำหรับใบของผู้ลงนาม (เช่น NRCA ของ ETDA, CA ไทย) จะเพิ่มในระยะ V2 เป็นรายการที่ผู้ดูแลจัดการเอง

## ขั้นตอนตรวจต่อลายมือชื่อ

1. **ความครบถ้วน** — hash ของข้อมูลตาม ByteRange ตรงกับ `messageDigest` และลายมือชื่อตรงกับ public key ของผู้ลงนาม (`adbe.pkcs7.sha1`: เทียบ SHA-1 ที่ฝังไว้กับเอกสารด้วย)
2. **ครอบคลุมเอกสาร** — ByteRange จบที่ท้ายไฟล์ (ยอม whitespace) ไม่จบ = มีการเพิ่มเติมหลังลงนาม (คำเตือน ไม่เปลี่ยนผล เพราะอาจเป็นลายมือชื่อถัดไป)
3. **เวลาลงนาม** — เชื่อเฉพาะเวลาจาก timestamp token ที่ตรวจผ่าน (messageImprint = hash ของค่าลายมือชื่อ, สายใบ TSA ถึง root ที่เชื่อถือ) ไม่มี = ใช้เวลาปัจจุบันในการตรวจ และแสดงเวลาที่ผู้ลงนามระบุ (`signingTime` / `/M`) ว่า "ไม่ได้รับรอง"
4. **สายใบรับรอง** — แยก "ถึง root ที่เชื่อถือได้ไหม" ออกจาก "ใบยังใช้ได้ ณ เวลาลงนาม" (ตรวจซ้ำที่เวลาภายในอายุใบ)
5. **การเพิกถอน** — ใบของ มมส.: ตาราง `certificates` (ข้อมูลต้นทางของ CRL) ต้องตรงทั้ง serial และ fingerprint; เพิกถอนหลังเวลาที่ประทับ = ยังถูกต้อง; ใบของ CA อื่น = ตรวจไม่ได้ (V1)
6. **การใช้งานของใบ** — EKU ยอม `emailProtection`, documentSigning, Microsoft/Adobe document signing, anyEKU หรือไม่ระบุ; keyUsage ต้องมี digitalSignature หรือ nonRepudiation
7. ลายมือชื่อแบบประทับเวลาทั้งเอกสาร (`ETSI.RFC3161`) ตรวจเหมือน timestamp token โดย imprint = hash ของข้อมูลตาม ByteRange

## ระดับผล

| ผล | เงื่อนไข |
|---|---|
| `valid` ถูกต้อง | ครบถ้วน + ถึง root ที่เชื่อถือ + ไม่ถูกเพิกถอน + ใบใช้ได้ ณ เวลาลงนาม + การใช้งานของใบถูกต้อง |
| `unknown` ไม่ทราบความถูกต้อง | ครบถ้วน แต่ไม่ถึง root ที่เชื่อถือ / ตรวจการเพิกถอนไม่ได้ / ใบหมดอายุแล้วและไม่มีการประทับเวลา / รูปแบบหรืออัลกอริทึมไม่รองรับ |
| `invalid` ไม่ถูกต้อง | hash หรือลายมือชื่อไม่ตรง, ข้อมูลลายมือชื่อเสียหาย, ใบถูกเพิกถอน (ก่อนเวลาที่ประทับ หรือไม่มีการประทับ), ใบหมดอายุ ณ เวลาที่ประทับ |

## ระยะการพัฒนา

| ระยะ | งาน | สถานะ |
|---|---|---|
| V1 | หน้า `/verify` + `POST /verify/pdf`: ความครบถ้วน, ครอบคลุมเอกสาร, สายใบถึง TUC, การเพิกถอนของใบ มมส. จากฐานข้อมูล, timestamp token, ประทับเวลาทั้งเอกสาร, nginx | เสร็จ |
| V2 | รายการ trust anchor ที่ผู้ดูแลจัดการ (`trust_anchors`, permission `trust_anchor:manage` — รอยืนยัน) + CA สาธารณะ + OCSP/CRL ออนไลน์ (กัน SSRF) + ข้อมูลเพิกถอนที่ฝังมา (LTV) + ตรวจการเพิกถอนของ Intermediate | ยังไม่ทำ |
| V3 | วิเคราะห์ลายมือชื่อแบบรับรองเอกสาร (DocMDP) ว่าการแก้ไขหลังลงนามได้รับอนุญาตหรือไม่, รายงานผลเป็น PDF | ยังไม่ตัดสินใจ |
